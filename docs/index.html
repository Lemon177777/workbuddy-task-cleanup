Why

删掉的对话，文件并没有跟着走

WorkBuddy 用久了，磁盘上会悄悄堆起一批"孤儿"—— 任务记录删了，但磁盘上的缓存、转录、日志还留着。

💾磁盘莫名少了几 GB

删掉的对话，磁盘上的文件并没有跟着一起走。用时无感，翻目录时心惊。

🗑️侧边栏没了，空间还占着

任务记录删了，但 tasks/、changes-detail/、projects/ 下的数据留了下来。

📁一串时间戳目录

每次新建对话都会生成一个 playground 工作区，对话删了，目录还在。

🧹想清理又不敢下手

分不清哪个目录属于"活着的"任务，删错了就回不来 —— 这才是最劝退的。

🐌索引与日志越来越臃肿

traces/ 和沙箱日志能悄悄涨到好几个 GB，却没人提醒你。

⏰不敢清，怕删掉定时任务的目录

自动化任务的工作目录不在会话列表里，肉眼根本看不出来，删错就悄悄断了定时任务 —— 所以本工具替你查。

Protection

三重保护 —— 宁可少删，不可错删

这是 v1.1 最重要的改动，补上了 v1.0 的两个盲区。清理前先建三个保护集合，任一命中，绝不删除。

🔎保护集合是每次现算的

每次扫描与清理都会重新读一遍数据库、实时构建保护集合，不会用过期的缓存下判断。automations 表还会按 deleted_at IS NULL 过滤 —— 已删除的旧任务不会被误当成"还在用"。

🩺顺带体检你的自动化任务

如果某条自动化任务指向的工作目录已经不存在（运行时必然失败），扫描会把它列为体检项单独提醒你 —— 一个清理工具，顺手做了一件排障的事。

✅ 被保护的工作区会出现在报告里，并注明原因（属于哪个存活会话 / 被哪个自动化任务引用）。此外，若某条自动化任务引用的目录已经不存在，扫描会把它列为体检项提醒你。
Principle

凭什么判断"这是垃圾"

不猜、不看目录时间、不信侧边栏 —— 只认数据库里的权威字段：sessions.deleted_at 与 automations.cwds。

~/.workbuddy/workbuddy.db · sessions 表 
-- 唯一权威判定依据（脚本以 mode=ro 只读打开，绝不写入）
SELECT id, cwd, title, deleted_at FROM sessions;

deleted_at IS NULL   → ✅ 存活会话   其数据一律不动
deleted_at 有值      → 🗑️ 已删除任务  磁盘残留即"垃圾"
workbuddy.db · automations 表 —— v1.1 新增的保护依据 
-- 自动化任务的工作目录不在 sessions 表里，必须单独查
SELECT id, name, status, cwds, deleted_at FROM automations;

cwds 是 JSON 数组，不是普通字符串 —— 直接按逗号切会解析失败
必须过滤 deleted_at IS NULL，否则会把已删的旧任务也算进来造成误报

→ 被引用的工作目录一律保护，绝不删除

❌不能看目录时间

存活会话的缓存也可能很久没更新，会误伤。

❌不能看目录是否为空

空目录也可能正被存活会话引用着。

❌不能信侧边栏列表

那只是快照，而且不含后台任务。

Tiers

四级分级，分开确认

不同级别的风险天差地别。所以拆开处理 —— 低风险的批量清，动到你成果的逐个过目。

级别内容典型路径风险实测体量
A 内部缓存与会话转录 tasks/ changes-detail/ file-history/ projects/ 🟢 低≈ 128 MB
B1 真 · 空壳工作区
无用户文件 且 无记忆		 ~/WorkBuddy/<时间戳>/ 🟢 低≈ 16 KB
B2 含成果文件 或 工作区记忆的孤儿工作区 里面还有你的报告 / 源码 / 图片 / .workbuddy/memory/ 🔴 高≈ 146.5 MB
C 诊断日志与运行追踪 traces/ logs/<日期>/ logs/sandbox/ 🟡 中≈ 2.75 GB
🔒 受保护 被存活会话或自动化任务引用的工作区 删掉可能悄悄打断你的定时任务 ⛔ 绝不删除—
⚠️ B2 是唯一需要逐个人工过目的类别 —— 那里面装的是你自己的劳动成果，或该项目的长期记忆，不是缓存。删 C 之前也请想清楚：删完就失去了历史排障线索。

📌 v1.1 修正：B1 的判定从「只剩 .workbuddy」收紧为「既无用户文件、也无工作区记忆」。含记忆的目录一律升级为 B2 —— 记忆优先，宁可留着。

# ② 预览将删除的内容（默认 dry-run，不落盘）

python scripts/wb_clean.py --tiers A,B1,C,B2 --include-b2 --apply

# ⑤ 二次核验（务必重跑一次，删除钩子可能延迟落盘）
python scripts/wb_scan.py
更多实用姿势 
# 永久删除（绕过回收站）—— 必须显式声明
python scripts/wb_clean.py --tiers A,B1,C --apply --no-trash

# 清 B2，但保留指定的那几个目录
python scripts/wb_clean.py --tiers A,B1,C,B2 --include-b2 --apply \
    --keep-b2 "2026-09-14-22-35-03"

# 只清 30 天前的旧数据，并留一份删除清单
python scripts/wb_clean.py --tiers C --older-than 30 --apply --log clean.json

# 挂定时任务：有残留时退出码 1
python scripts/wb_scan.py --check
参数默认说明
--tiers A,B1,C必填要处理的类别，逗号分隔：A B1 B2 C
--apply关闭真正执行。不加时只预览，不落盘
--to-trash / --no-trash--to-trash移入回收站（默认）/ 永久删除
--include-b2关闭清理 B2 的必要开关（含用户文件或记忆）
--keep-b2 NAMES—B2 中要保留的目录名，逗号分隔
--older-than DAYS—只清理修改时间早于 N 天的项
--log FILE—把删除清单写入 JSON 留痕
--json OUT—（仅 scan）额外导出一份 JSON 报告
--check—（仅 scan）有残留或异常时退出码 1

Safety

安全设计

这是一个"会删文件"的工具。所以默认动作必须是保守的，任何"多做一步"都需要你显式授权。

①默认 dry-run

不加 --apply，脚本只打印"将删什么"，绝不动盘。

②回收站优先

执行时默认移入回收站；永久删除必须显式加 --no-trash。

③双重显式授权

B2 必须同时给出 --tiers B2 和 --include-b2。

④事后完整性校验

每次清理后自动检查存活会话工作区，缺失必须为 0。

1

先扫描 → 后呈现 → 再确认 → 末执行，顺序不可颠倒。

2

不动数据库。只读打开（mode=ro），绝不写入一个字节。

3

不碰 blobs/ —— 那是内容寻址存储，存活任务也在引用，删了会破坏数据。

4

不删任何被自动化任务引用的工作目录 —— 删掉等于悄悄打断用户的定时任务。

5

不把含 .workbuddy/memory/ 的工作区当空壳 —— 那是项目长期记忆。

6

B2 必须逐个列文件 + 二次确认 —— 那是你的成果或记忆，不是缓存。

7

默认走回收站；要永久删除才加 --no-trash，且先加粗警告、列出受影响路径。

8

删完必须二次核验，并报告「存活会话工作区缺失 = 0」。

9

保留当天的日志 logs/<今天>/ 与 logs/sandbox/<今天>/。

10

改动脚本后先跑 wb_selftest.py，23 项全绿再交付。

FAQ

常见问题

会删掉我正在使用的对话吗？

不会。判定只依据 sessions.deleted_at：IS NULL 的存活会话，其工作区与数据一律跳过。脚本还会自动把当前正在运行的会话工作区排除在外，清理后额外校验一次完整性。

会误删我定时任务的工作目录吗？v1.1

不会。这是 v1.1 专门补上的保护：脚本会读 automations.cwds（过滤掉已删除的自动化），把被引用的目录并入保护集合。

这类目录往往没有任何存活会话引用 —— v1.0 会把它当孤儿删掉，那正是要修的问题。

什么是「工作区记忆」？为什么不能删？v1.1

工作区目录下的 .workbuddy/memory/ 存放着该项目的长期记忆与每日工作日志：

<工作区>/.workbuddy/memory/ → YYYY-MM-DD.md · automations/<id>/memory.md

一个目录可能看起来"只剩 .workbuddy 了"，但里面恰恰只有记忆。v1.0 会把它判成空壳并删除；v1.1 改为含记忆即升级为 B2，列出记忆文件，由你确认。

删了还能恢复吗？

默认可以。执行时脚本走系统回收站（Windows 用 SHFileOperationW，macOS 用 ~/.Trash，Linux 用 freedesktop 规范）。只有显式加 --no-trash 才是永久删除。

我删掉的对话里的文件，还能找回来吗？

只要还没清理过，它们大概率还躺在 ~/WorkBuddy/<时间戳>/ 里 —— 这正是 B2 存在的意义。把它们找回来，是可回收的那 146 MB 之外、更值钱的东西。

为什么清理完，目录好像还在？

这是本机 safe-delete 钩子的已知行为：删除会被转成回收站操作，且可能在 rmtree() 返回之后才真正落盘。所以必须重跑一次 wb_scan.py 做二次核验，不要仅凭第一轮输出下结论。

logs/sandbox 整目录删除失败？

已知坑。整目录删会报 Some operations were aborted，必须按日期子目录（如 20261009/）逐个删。脚本已经这么做了，并且会保留当天。

macOS / Linux 能用吗？

能。两个脚本纯标准库，路径基于 ~/.workbuddy 与 ~/WorkBuddy，三个平台通用。用 python3 代替 python 即可。

会不会动到我自己的项目文件？

不会。清理范围只有两处：~/.workbuddy/ 内部的缓存与日志，以及 ~/WorkBuddy/<时间戳>/ 下的孤儿工作区。你在别处创建的项目目录，不在扫描范围内。

能不能定期自动清理？

可以配一个定时任务只跑只读盘点，把报告推给你；但删除动作建议始终保留人工确认 —— 尤其 B2，那是你的成果文件，不该被自动化悄悄带走。

删掉的对话，别再占着你的硬盘。
